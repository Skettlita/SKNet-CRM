# Autenticación y permisos
/login, /signup, /recover y /app/* para ISP; /admin/login, /admin/* y recuperación administrativa separada. Sin enlace SaaS desde login ISP, sin signup SaaS. Una identidad ISP pertenece a una empresa en V1. Usuario o correo + contraseña en ambos logins: username y correo obligatorios, únicos sin distinguir mayúsculas dentro de cada ámbito; username sin @, normalizar y validar; correo verificado cuando SMTP disponible. Scope derivado del endpoint y sesión, nunca del cliente. Sesión revocable con token aleatorio hash en BD, cookie HttpOnly, SameSite, Secure bajo HTTPS, CSRF según estrategia; Argon2id, rate limiting, errores genéricos. Logout invalida sesión; no secretos en logs.
Primer administrador SaaS por CLI interactiva segura, no seed contraseña, uno inicialmente; luego personal SaaS solo por administradores con permisos. No OWNER obligatorio. No eliminar/desactivar último admin capaz ni permitir autoescalación. Signup configurable por SaaS (apagado inicialmente hasta habilitar): empresa, NIT opcional, teléfono, nombre admin, username, email, contraseña/confirmación y aceptación términos. Crear empresa, usuario, membresía, rol inicial, suscripción trial gratuita sin vencimiento y auditoría en transacción. No collector ni datos ficticios. Registro manual SaaS equivalente. Empleados ISP creados/invitados por personal autorizado de su propia empresa, contraseña temporal segura con cambio obligatorio en laboratorio; SMTP cuando disponible. Reset admin SaaS por CLI de emergencia; ISP admin por correo o soporte autorizado con identidad verificada; empleados por admin autorizado. Revocar sesiones y auditar reset sin secretos. No afirmar envío email si SMTP no disponible.
Roles personalizables y permisos granulares por recurso/acción; múltiples roles, acceso efectivo = ámbito + empresa + suscripción/feature implementada + permiso + recurso autorizado; SaaS no recibe automáticamente acceso ilimitado a datos CRM. Soporte explícito auditado si se habilita. API rechaza acciones no autorizadas, 403/404 según caso; probar IDOR. Sidebar, tarjetas, botones, exportaciones, búsquedas, rutas y datos según permisos efectivos; grupos vacíos ocultos. Sin selector SaaS/ISP de demo. MFA y revisión de seguridad antes de exposición comercial.

## Parámetros iniciales de la fase 2

- Cookies de sesión separadas por ámbito y ruta, con 12 horas de vigencia absoluta. Verificación de origen en todas las operaciones que cambian datos. Para DEV con HTTPS o un proxy TLS, define `SKNET_ORIGIN` y `SKNET_COOKIE_SECURE=1`.
- El límite inicial es de ocho intentos por identificador y 150 por origen de red observado, por acción y ámbito durante 15 minutos. Con un proxy que no aporta una IP de cliente de confianza, el límite por origen se comparte entre los clientes de ese proxy.
- ACCESS habilita los módulos de esta fase según el plan, además de exigir sus permisos. El conteo de usuarios activos incluye al administrador inicial. Los cambios al plan de prueba crean una versión y preservan las versiones asignadas.
- La autenticación con contraseña temporal solo se permite una vez. La sesión inicial se limita a elegir una nueva contraseña y las operaciones mínimas de sesión. El titular de un correo puede confirmarlo desde el perfil cuando SMTP está configurado. Los enlaces usan fragmentos de URL para que el token no llegue al registro HTTP del servidor.
