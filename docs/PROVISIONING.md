# Provisioner — reglas V1 (acordadas)

Una instalación = un Docker Engine Linux, una BD y sus propios secretos. 4 contenedores base y un collector por empresa que activa monitoreo. El provisioner, no FastAPI, administra el socket Docker, que equivale a privilegios elevados sobre el host. No exponer ese socket ni aceptar comandos arbitrarios. Las imágenes, capacidades y montajes se definen mediante una plantilla controlada. El collector usa NET_ADMIN/NET_RAW para el laboratorio; no privileged ni host networking. Restringir forwarding y conexiones entre redes y acceso al host. Los collectors usan API autenticada; no credenciales PostgreSQL. Producción requiere TLS y revisión del aislamiento.

## Recursos
Valores de laboratorio configurables, no hardcodeados ni asignados por adelantado:
- Pool Docker: 172.20.0.0/16, subred /30 por collector; gateway = red+1, contenedor = red+2.
- Pool WireGuard: 10.200.1.0/24, subred /31 por túnel; collector = primera IP, MikroTik = segunda IP (modelo probado).
- Puertos UDP del host: 51820–51919, inclusivos; puerto interno 51820 por contenedor.
- Endpoint GNS3: 192.168.42.31; host Ubuntu: 10.200.0.254. Provisioner crea DST-NAT por puerto mediante API RouterOS de R.SKNet, conservando puerto hacia Ubuntu, y verifica reglas de forward apropiadas. Automatización NAT es parte del MVP. En laptop usar endpoint real alcanzable o marcar pendiente; Docker Desktop puede requerir ajustes de red/kernel.
- Ejemplo ISP1: 172.20.0.0/30, 10.200.1.0/31, UDP 51820. ISP2: 172.20.0.4/30, 10.200.1.2/31, UDP 51821. Cada uno puede monitorear su propia 192.168.1.0/24. Con los rangos ilustrativos el límite teórico inicial es 100 collectors por puertos (no capacidad real de CPU/RAM ni de red; /24 da 128 túneles y /16 da 16384 bloques /30). Reducir/aumentar según infraestructura.

## Proceso
1. Verificar permiso, suscripción, límites, empresa activa y ausencia de otro collector vigente. El usuario pulsa Conectar mi red y Generar script; esa solicitud dispara el trabajo asíncrono persistente, no un botón Crear collector. Si ya existe collector, mostrar estado/script y permitir reintento o cambios sobre el mismo. No reservar nada por el mero signup.
2. Reservar de forma atómica un conjunto libre de recursos, usando bloqueo transaccional global de asignación e índices únicos. Revisar redes/puertos existentes en Docker y host, incluido el laboratorio anterior; rechazar solapamientos con redes locales de transporte, Docker, API y túnel en el namespace correspondiente, no prohibir redes privadas repetidas entre empresas. Verificar pertenencia a pool, rango, prefijos y capacidad. Si se agotan recursos, mostrar "Servicio temporalmente en mantenimiento", abrir/actualizar ticket SaaS con causa interna y referencia visible al ISP; CRM sigue operativo. No dejar contenedor parcial ni liberar reservas todavía ocupadas.
3. Generar clave privada local con WireGuard, conservar con permisos restringidos en almacenamiento persistente del host (referencia opaca en DB); almacenar clave pública y entregar solo esta al usuario. Token aleatorio por collector; almacenar hash en DB y secreto local de forma protegida. No enviar secretos a UI, logs ni Git.
4. Crear red y contenedor con labels de instalación/empresa/collector; publicar puerto host UDP hacia 51820. No añadir una red Docker compartida que cambie el aislamiento. Para API usar gateway de la red propia o una URL alcanzable validada desde eth0; evitar conflictos de rutas, restringir con firewall. El provisioner usa Docker SDK; un fallo real de bind debe dejar error y recursos reconciliables, no saltarse validación.
5. Crear y verificar regla DST-NAT propia mediante API RouterOS con etiqueta estable por instalación/collector (edge_rule_tag); verificar puerto, conflictos y firewall forward sin modificar reglas ajenas ni abrir acceso general. API con TLS cuando sea posible, credenciales privadas, usuario dedicado y red de gestión restringida; no exponer API al ISP. Si falla, no entregar script listo; reconciliar o compensar cambios de Docker/NAT, ticket automático deduplicado. Después mostrar script RouterOS 7 con endpoint, puerto, clave pública de SKNet, IP /31 del MikroTik, AllowedIPs/allowed-address de la IP de túnel del collector, keepalive 25 s y comando para obtener la clave pública del MikroTik. Mostrar instrucciones de firewall input/forward y retorno solo para redes de gestión autorizadas; no abrir todo el router ni aplicar scripts remotos automáticamente. El cliente ejecuta el script y aporta su clave pública y CIDR autorizados. Validar clave WireGuard base64 de 32 bytes y no usar clave privada del cliente.
6. Configurar peer local con la IP de túnel remota /32 y los CIDR autorizados. No permitir 0.0.0.0/0 ni rutas que capturen la API o interfaces locales; solo IPs de gestión autorizadas. La IP del servicio dinámica no se monitorea por defecto. Montar config persistente; levantar wg0 automáticamente al iniciar el collector, incluyendo reinicios. Usar rutas derivadas del bloque reservado y la configuración de red; no duplicar direcciones de gestión en otras tablas.
7. Verificar handshake y prueba activa ICMP al MikroTik; READY de aprovisionamiento solo con configuración exitosa y conectividad comprobada. Separar estado de aprovisionamiento, contenedor, heartbeat y salud de VPN. Puede pasar de READY a VPN DISCONNECTED sin recrear contenedor. Los estados visibles combinan estos campos.
8. Permitir reintentar una operación fallida conservando reserva y claves; reconciliar con Docker por labels/ID y estado deseado tras reinicio. Actualizar peer y rutas en el mismo collector de forma controlada; incrementar revisiones de configuración pertinentes. No duplicar contenedores, claves ni puertos por reintentos concurrentes.
9. Deshabilitar conserva historial y recursos; retirar definitivamente revoca token, detiene y elimina únicamente recursos propios, retira secretos y libera la reserva solo después de comprobar que Docker y las reglas NAT propias ya no los utilizan. Un fallo de limpieza queda pendiente de reconciliación. No eliminar mediciones ni incidentes al retirar.

## Estados
PENDING → PROVISIONING → WAITING_PUBLIC_KEY → WAITING_HANDSHAKE → READY. ERROR permite reintento, DISABLED suspende. Estado VPN independiente: UNKNOWN, CONNECTED, DISCONNECTED. Heartbeat reporta vida del collector aunque no tenga peer configurado. Los jobs se procesan de uno en uno por collector; clave de idempotencia y recuperación de jobs interrumpidos. No registrar claves privadas ni tokens en mensajes de error. Redundancia de túnel y Kubernetes quedan fuera del MVP. Integración API RouterOS para administración de routers de clientes (PPPoE/DHCP) también queda fuera, pero NAT del router propio sí entra.

## Consideraciones operativas
Usar interfaz WAN y/o destino configurados según instalación. No sobrescribir regla existente ajena; si hay colisión, elegir otro puerto. Identificar reglas por etiqueta estable y verificar su contenido; IDs efímeros no son fuente única. Solo eliminar reglas propias al retirar definitivamente. Si varios entornos usan el mismo router/host, pools/puertos y etiquetas deben ser disjuntos o usar routers separados; nunca operar PROD desde DEV/TEST. El provisioner usa adaptador RouterOS comprobable y mock solo en tests; si falta acceso real, mostrar pendiente/error, no afirmar éxito. Los pools ilustrativos no se consideran libres sin inspección.
