# Provisioner — reglas V1 (acordadas)

Una instalación = un Docker Engine Linux, una BD y sus propios secretos. 4 contenedores base y un collector por empresa que activa monitoreo. El provisioner, no FastAPI, administra el socket Docker, que equivale a privilegios elevados sobre el host. No exponer ese socket ni aceptar comandos arbitrarios. Las imágenes, capacidades y montajes se definen mediante una plantilla controlada. El collector usa NET_ADMIN/NET_RAW para el laboratorio; no privileged ni host networking. Restringir forwarding y conexiones entre redes y acceso al host. Los collectors usan API autenticada; no credenciales PostgreSQL. Producción requiere TLS y revisión del aislamiento.

## Recursos
Valores de laboratorio configurables, no hardcodeados ni asignados por adelantado:
- Pool Docker: 172.20.0.0/16, subred /30 por collector; gateway = red+1, contenedor = red+2.
- Pool WireGuard: 10.200.1.0/24, subred /31 por túnel; collector = primera IP, MikroTik = segunda IP (modelo probado).
- Puertos UDP del host: 51820–51919, inclusivos; puerto interno 51820 por contenedor.
- Endpoint GNS3: 192.168.42.31; host Ubuntu: 10.200.0.254. Provisioner crea DST-NAT por puerto mediante API RouterOS de R.SKNet, conservando puerto hacia Ubuntu, y verifica reglas de forward apropiadas. Automatización NAT es parte del MVP. En laptop usar endpoint real alcanzable o marcar pendiente; Docker Desktop puede requerir ajustes de red/kernel.
- Ejemplo ISP1: 172.20.0.0/30, 10.200.1.0/31, UDP 51820. ISP2: 172.20.0.4/30, 10.200.1.2/31, UDP 51821. Cada uno puede monitorear su propia 192.168.1.0/24. Con los rangos ilustrativos el límite teórico inicial es 100 collectors por puertos (no capacidad real de CPU/RAM ni de red; /24 da 128 túneles y /16 da 16384 bloques /30). Reducir/aumentar según infraestructura.

## Proceso
1. Verificar permiso, suscripción, límites, empresa activa y ausencia de otro collector vigente. El usuario pulsa Conectar mi red y Generar script; esa solicitud dispara el trabajo asíncrono persistente, no un botón Crear collector. Si ya existe collector, mostrar estado/script y permitir reintento o cambios sobre el mismo. No reservar nada por el mero signup.
2. Reservar de forma atómica un conjunto libre de recursos, usando bloqueo transaccional global de asignación e índices únicos. Revisar redes/puertos existentes en Docker y host, incluido el laboratorio anterior; rechazar solapamientos con redes locales de transporte, Docker, API y túnel en el namespace correspondiente, no prohibir redes privadas repetidas entre empresas. Verificar pertenencia a pool, rango, prefijos y capacidad. Si se agotan recursos, mostrar "Servicio temporalmente en mantenimiento", abrir/actualizar ticket SaaS con causa interna y referencia visible al ISP; CRM sigue operativo. No dejar contenedor parcial ni liberar reservas todavía ocupadas.
3. Generar clave privada local con WireGuard, conservar con permisos restringidos en almacenamiento persistente del host (referencia opaca en DB); almacenar clave pública y entregar solo esta al usuario. Token aleatorio por collector; almacenar hash en DB y secreto local de forma protegida. No enviar secretos a UI, logs ni Git.
4. Crear red y contenedor con etiquetas de instalación, empresa y collector. Publicar únicamente el puerto UDP asignado hacia el puerto interno configurado. Backend, provisioner y collector usan REST sobre sockets Unix. El provisioner y los collectors usan volúmenes separados. Cada collector usa su propio token y recibe solo su configuración. El agente limita el tráfico de la interfaz Ethernet y descarta el forwarding.
5. Crear y verificar regla DST-NAT propia mediante API RouterOS con etiqueta estable por instalación/collector (edge_rule_tag); verificar puerto, conflictos y firewall forward sin modificar reglas ajenas ni abrir acceso general. API con TLS cuando sea posible, credenciales privadas, usuario dedicado y red de gestión restringida; no exponer API al ISP. Si falla, no entregar script listo; reconciliar o compensar cambios de Docker/NAT, ticket automático deduplicado. Después mostrar script RouterOS 7 con endpoint, puerto, clave pública de SKNet, IP /31 del MikroTik, AllowedIPs/allowed-address de la IP de túnel del collector, keepalive 25 s y comando para obtener la clave pública del MikroTik. Mostrar instrucciones de firewall input/forward y retorno solo para redes de gestión autorizadas; no abrir todo el router ni aplicar scripts remotos automáticamente. El cliente ejecuta el script y aporta su clave pública y CIDR autorizados. Validar clave WireGuard base64 de 32 bytes y no usar clave privada del cliente.
6. Configurar peer local con la IP de túnel remota /32 y los CIDR autorizados. No permitir 0.0.0.0/0 ni rutas que capturen la API o interfaces locales; solo IPs de gestión autorizadas. La IP del servicio dinámica no se monitorea por defecto. Montar config persistente; levantar wg0 automáticamente al iniciar el collector, incluyendo reinicios. Usar rutas derivadas del bloque reservado y la configuración de red; no duplicar direcciones de gestión en otras tablas.
7. Verificar handshake y prueba activa ICMP al MikroTik; READY de aprovisionamiento solo con configuración exitosa y conectividad comprobada. Separar estado de aprovisionamiento, contenedor, heartbeat y salud de VPN. Puede pasar de READY a VPN DISCONNECTED sin recrear contenedor. Los estados visibles combinan estos campos.
8. Permitir reintentar una operación fallida conservando reserva y claves; reconciliar con Docker por labels/ID y estado deseado tras reinicio. Actualizar peer y rutas en el mismo collector de forma controlada; incrementar revisiones de configuración pertinentes. No duplicar contenedores, claves ni puertos por reintentos concurrentes.
9. Deshabilitar revoca el token, retira la regla NAT propia y conserva el contenedor detenido y la reserva. Retirar elimina solo el contenedor y la red identificados por etiqueta. La reserva se libera después de verificar que esos recursos y la regla NAT ya no existen. Los volúmenes y el historial se conservan. El token retirado permanece revocado.

## Estados
PENDING → PROVISIONING → WAITING_PUBLIC_KEY → WAITING_HANDSHAKE → READY. ERROR permite reintento, DISABLED suspende. Estado VPN independiente: UNKNOWN, CONNECTED, DISCONNECTED. Heartbeat reporta vida del collector aunque no tenga peer configurado. Los jobs se procesan de uno en uno por collector; clave de idempotencia y recuperación de jobs interrumpidos. No registrar claves privadas ni tokens en mensajes de error. Redundancia de túnel y Kubernetes quedan fuera del MVP. Integración API RouterOS para administración de routers de clientes (PPPoE/DHCP) también queda fuera, pero NAT del router propio sí entra.

## Consideraciones operativas
El destino WAN depende de la instalación. El adaptador evita las reglas ajenas al elegir un puerto e identifica las reglas propias por etiqueta estable y contenido. Deshabilitar o retirar una conexión solo afecta su regla propia. Si varios entornos usan el mismo host o router, deben usar pools, puertos y etiquetas disjuntos. DEV usa el adaptador simulado y el modo real exige TLS y verificación de NAT. Antes de asignar recursos, se inspeccionan los pools ilustrativos.

## Preparación futura para Ubuntu TEST

1. Prepara un Docker Engine Linux dedicado y verifica WireGuard en el kernel y soporte de iptables/nftables. Construye una imagen local etiquetada para TEST. Mantén base, volúmenes de secretos, sockets y etiquetas separados de DEV. El overlay TEST requiere integrar expresamente los montajes de socket y secretos usados por DEV y permitir al provisioner llegar solo a la API RouterOS por la red de gestión.
2. Inventaría subredes Docker, del host y RouterOS. Configura `SKNET_DOCKER_POOL`, `SKNET_WG_POOL`, `SKNET_PROTECTED_NETWORKS`, `SKNET_UDP_FIRST`, `SKNET_UDP_LAST`, `SKNET_UDP_INTERNAL`, `SKNET_UDP_BIND`, `SKNET_WG_ENDPOINT` y un `SKNET_INSTALLATION_ID` exclusivo. `SKNET_UDP_BIND` es la IP concreta de Ubuntu que recibe DST-NAT. `SKNET_WG_ENDPOINT` es la IP o el DNS que alcanzará el router cliente.
3. Para habilitar `SKNET_CONNECTIVITY_MODE=routeros`, configura en el worker `SKNET_ROUTEROS_URL` como origen HTTPS, `SKNET_ROUTEROS_WAN` como destino público de las reglas, `SKNET_ROUTEROS_TARGET` con la misma IP que `SKNET_UDP_BIND`, `SKNET_ROUTEROS_FORWARD_TAG`, `SKNET_ROUTEROS_USER` y `SKNET_ROUTEROS_PASSWORD_FILE` como ruta de un secreto montado solo lectura. Usa `SKNET_ROUTEROS_CA_FILE` si el certificado requiere una CA interna. Restringe el usuario y el acceso de red a lectura del firewall y gestión de NAT en la medida que permitan las políticas RouterOS de ese equipo.
4. Prepara y revisa una regla de forward activa y etiquetada para UDP hacia la IP y rango de Ubuntu, con `connection-nat-state=dstnat`, antes de reglas que descarten ese tráfico. El adaptador verifica su presencia y el orden de las reglas compatibles. El operador debe comprobar además el firewall de Ubuntu, acceso desde WAN, rutas de retorno, ICMP restringido al túnel y aislamiento bajo la configuración de TEST.
5. Verifica alta, repetición, rotación, reinicio, retiro controlado, TLS y pérdidas de disponibilidad con un router autorizado para TEST. Debe fallar de forma visible si falta NAT, forwarding o la clave del peer. Una publicación UDP ocupada por un proceso externo al inventario Docker se detecta al crear o arrancar el contenedor. La reserva se conserva hasta reconciliar la causa.

No se aplicó esta configuración en Ubuntu TEST. En DEV, el adaptador simulado se identifica en las pantallas, en la API y en la vista previa del script.

## Actualizar y reconciliar collectors

En **SaaS → Collectors** se compara la imagen observada en el contenedor con el identificador al que apunta la etiqueta configurada en `SKNET_COLLECTOR_IMAGE`. La opción **Actualizar collector** requiere un collector operativo, una candidata distinta y que no haya otro trabajo activo. Construir o etiquetar una imagen no solicita actualizaciones.

1. Conserva localmente las dos imágenes. Etiqueta el identificador actualmente desplegado, por ejemplo `docker tag sha256:ID_ANTERIOR sknet-collector:respaldo-test`, y construye la imagen candidata con la etiqueta configurada para ese entorno.
2. Solicita **Actualizar collector** y confirma la imagen que muestra el panel. El trabajo guarda los dos IDs inmutables. El provisioner verifica propiedad, red, volúmenes y puertos. Reemplaza el contenedor con la misma identidad, token, red asignada, IP, puerto y volumen.
3. El backend exige un heartbeat posterior al reemplazo con la revisión vigente. El provisioner comprueba la imagen, el contenedor en ejecución y la clave pública WireGuard aplicada. El trabajo guarda el resultado y el nuevo identificador del contenedor. La VPN vuelve a comprobarse por el flujo normal del collector.
4. Si la nueva imagen falla, el worker intenta recuperar la anterior y la verifica de nuevo. **Trabajos** registra el fallo y, si se verificó la reversión, muestra **Imagen anterior restaurada y verificada**. La actualización no llama al adaptador de RouterOS. Puede haber un intervalo sin mediciones durante el reemplazo y la reversión.

**Reconciliar** permite a SaaS reparar un collector habilitado aun dentro de la ventana automática de 15 minutos. Recrear un contenedor perdido usa el último ID de imagen aprobado si se conoce. **Reintentar** actúa sobre trabajos fallidos. **Deshabilitar** corta el uso sin liberar la reserva. **Retirar definitivamente** verifica la desaparición del contenedor y de la red antes de liberar la reserva. Los volúmenes de identidad y datos se conservan.

**Recursos de red** informa contenedores, redes y volúmenes con etiquetas de la instalación que carecen de una referencia vigente. Los volúmenes que pertenecen a un collector retirado aparecen como conservados. Ante una investigación, verifica primero las tres etiquetas de propiedad, la reserva en la base, las conexiones del recurso y, para volúmenes, la existencia de una copia protegida. El detector solo informa.

`POST /api/v1/admin/connectivity/collectors/{company}/{collector}/upgrade` y `/reconcile` requieren `connectivity.write` en SaaS. Los listados `/admin/connectivity/collectors`, `/jobs` y `/pools` exponen el estado de imágenes, trabajos y residuos. El canal del worker permanece en el socket privado.
